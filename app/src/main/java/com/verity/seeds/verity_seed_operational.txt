D2 — ROUTE, CHROME, AND VIEWMODEL BOUNDARIES (CLARIFICATION)

Context:
During D2 execution, ambiguity was encountered around where Workspace chrome,
ViewModel ownership, and Compose Route boundaries should live.

This section records the clarified, law‑correct interpretation for D2+ work.

Authoritative Clarifications:

• The Invoice Workspace remains the *conceptual anchor* of the app,
  but it is NOT the lifecycle owner of application chrome.

• MainActivity (or a future NavHost root) remains the single lifecycle root.
  It owns:
  – ViewModel instantiation
  – Chrome rendering (Top App Bar, global navigation affordances)
  – System UI integration (insets, status bar, back handling)

• Feature modules (e.g. feature/invoice):
  – MAY define ViewModel types
  – MAY expose Route composables
  – MUST NOT own ViewModel lifecycles
  – MUST NOT decide chrome rendering directly

• A Route is the ONLY place where:
  – ViewModels are referenced
  – StateFlows are collected
  – UI state is adapted for rendering

• Screens remain pure UI and never reference ViewModels or Flows.

Chrome-Specific Rule (Locked):

• Workspace chrome intent (title, subtitle, actions) is expressed
  declaratively via WorkspaceChromeSpec.
• WorkspaceChromeSpec is PRODUCED by workspace‑related ViewModels
  and CONSUMED by the root UI frame.
• The root frame decides *how* chrome is rendered, not *what* it is.

Operational Outcome:

• InvoiceWorkspaceViewModel producing WorkspaceChromeSpec is VALID.
• MainActivity collecting chromeSpec and rendering VerityTopAppBar is VALID.
• Embedding chrome rendering inside the Workspace screen is INVALID.

This clarification does not change any D2 scope or deliverables.
It removes ambiguity to prevent architectural drift during execution.

Draft Lifecycle & Volatility (Operational, Locked)

• Drafts are UI-only workflow state and are not domain truth.
• Drafts are in-memory and disposable by design.
• Process death, background eviction, or app restart results in complete draft loss.

  reintroduced by future, explicit design.
• Only one active draft may exist at any time.
• Parallel drafts, multi-window draft editing, or background draft duplication
  are prohibited.
• External navigation or deep-links while a draft exists must require explicit
  user choice (continue or discard).

Resolved UX Direction — Autocomplete & Input Interactions (Locked)

Autocomplete behavior for input‑heavy atoms has now been explicitly designed
and is considered directionally locked. This section records execution‑level
UX rules; it does not alter domain, draft, or replay guarantees.

Resolved Interaction Model:
• Autocomplete is typing‑first and power‑user optimized.
• Input fields remain fully editable at all times.
• Suggestions are rendered inline (non‑popup) below the input field.
• Popup‑based components (e.g. DropdownMenu, Popup) are not used for autocomplete.
• Keyboard focus must never be interrupted while typing.
• Keyboard closes only on explicit suggestion selection or user dismissal.
• Suggestions may appear from the first character.
• Suggestions auto‑hide when empty.
• Selection commits value and collapses suggestions deterministically.

Visual & Surface Semantics:
• Autocomplete suggestions are treated as an expansion of the input field,
  not as a floating popup or menu.
• Visual continuity with the input field is mandatory (shape, border semantics).
• Popup affordances (elevation, shadow, decorative accents) are not used.
• Visual hierarchy is expressed via spacing, typography, and structure.
• Color usage follows semantic tokens defined in core/theme.
• Raw hex colors are not permitted in UI code.

Execution Notes:
• Autocomplete filtering and ranking logic is owned by screen‑level state
  (ViewModel / reducer), not by UI primitives.
• UI primitives receive pre‑filtered, ordered suggestion lists.
• Result capping and relevance ordering are required for performance and UX
  but are executed upstream.

D2.3 — Pre-Finalization Document Preview (OPERATIONAL, LOCKED)

Before finalization, users must be able to preview the document
(Invoice or Challan) exactly as it will appear once finalized.

The preview pipeline is backed by a canonical InvoiceDocumentModel derived via a pure Draft → Document projection; preview and finalization share this projection.

Preview semantics are strictly defined:

• Preview is a visual, read-only representation rendered from a deterministic
  snapshot of the current draft via a canonical document projection.
• Preview renders the authoritative document layout that will be used for
  final artifact generation, but NO PDF is generated during preview.
• Preview rendering is strictly side-effect free:
  – No persistence
  – No domain events
  – No artifact creation
• Preview displays the invoice number that will be used if the document is
  finalized. This number is tentatively allocated during draft creation and
  becomes authoritative only upon finalization.
• Preview contains no draft markings, watermarks, or “pending” indicators.
• Exiting preview always returns the user to the editable draft workspace
  without mutation, numbering side effects, or lifecycle transitions.

Preview is not a persistence step and produces no domain facts.
It is a UI-level, deterministic rendering of draft-derived state.

AMENDMENT VS NEW DOCUMENT SEMANTICS (FUTURE, LOCKED)

This section defines forward-looking but constitutionally locked semantics
for document correction and must not be violated by future implementation phases.

New Document (Reuse):
• Create from existing always produces a new, independent document.
• The source document remains immutable and historically correct.
• Reuse copies structure and values, never identity or compliance fields.
• This flow is forward-only and non-corrective.

Amendment (Correction):
• An amendment represents correction of a previously finalized document.
• Amendments are new documents, never edits or replacements.
• The original document is never mutated or deleted.
• Amendment relationships are additive domain facts
  (e.g. DocumentAmended events).
• Amendments must be explicitly initiated and clearly labelled.
• Amendments must never reuse Create-from-existing semantics.
• Projection layers may reflect supersession or net effects, but
  domain truth remains append-only.

Amendment workflows are deferred to D3+ but their semantics are locked.

Intent:
Support job‑work / repair workflows where goods move without sale,
work is performed later, and billing occurs independently of movement,

Flow:

  (e.g. product value ₹50,000; no sale).
• User finalizes the Challan.
• Challan receives its own document number and becomes immutable.
• No invoice reference is required at Challan finalization time.

• From the finalized Challan, user explicitly chooses
  “Create Job Work Invoice from this Challan”.
• A new Invoice draft is created and opened in the Workspace.

Draft Initialization Semantics:
Copied into the Invoice draft:
• Customer (Billed To / Shipped To configuration)
• Referenced product / goods description from the Challan
• Challan number as a source reference
• Applicable tax context (document‑type aware)

Not copied into the Invoice draft:
• Challan monetary value (goods value is not billed)
• Any finalized monetary totals
• Dates, payments, ledger effects
• Immutable or compliance identifiers

• User adds job‑work / service line items to the Invoice draft
  (e.g. ₹1,000 of work performed).
• User previews and finalizes the Invoice.
• Invoice receives its own document number and becomes immutable.


Linkage Semantics (Post‑Finalization):
• After Invoice finalization, a DocumentLinkCreated domain event is emitted:
  – sourceDocument: Challan
  – targetDocument: Invoice
  – relationType: JobWorkInvoice
• The Challan itself is never mutated.
• Linkage is derived into projections for navigation and visibility.

Artifact Generation Semantics (Bifurcated)

Challan artifact (PDF) generation is explicitly decoupled from Challan
domain finalization and follows one of two authoritative paths based on
declared business intent.

Path A — Standalone Challan

Intent:
The Challan represents goods movement without any associated Invoice.

Semantics:
• User creates and finalizes the Challan.
• Challan becomes immutable domain truth.
• A Challan PDF is generated immediately upon finalization.
• The generated PDF is authoritative and final.
• No Invoice linkage is expected or required.

Path B — Invoice‑Linked Challan (Job Work Flow)

Intent:
The Challan represents goods movement that will be billed via a subsequent
Job Work Invoice.

Semantics:
• User creates and finalizes the Challan with explicit linkage intent.
• Challan becomes immutable domain truth.
• No Challan PDF is generated at this stage.
• User creates an Invoice from the finalized Challan.
• User finalizes the Invoice.
• Document linkage is finalized via a DocumentLinkCreated event.
• Only after successful linkage is established:
  – A Challan PDF is generated.
  – The generated PDF includes the linked Invoice reference.
• The generated Challan PDF is authoritative and final.

Resolution Rules:
• A finalized Challan must explicitly declare whether it is Standalone or
  Invoice‑Linked at finalization time.
• An Invoice‑Linked Challan may not be dispatched or externally shared
  until its PDF artifact is generated.
• If an Invoice‑Linked Challan is abandoned (no Invoice created),
  the system must require an explicit resolution:
  – Convert to Standalone and generate PDF, or
  – Cancel the Challan.
• Challan PDFs are immutable once generated and are never regenerated.

Guarantees:
• Challan and Invoice are finalized independently.
• No document depends on future facts for finalization.
• Immutability is preserved for both documents.
• Circular dependency is resolved via additive linkage events.
• Search and document views clearly display the relationship once linked.
• Users never experience dual‑draft or co‑finalization ambiguity.

Constraints:
• Challan must always be finalized before its job‑work Invoice.
• An Invoice created via this flow must reference exactly one Challan.
• A Challan may link to at most one Invoice.
• Editing or mutating finalized documents is strictly prohibited.

Operational Laws (Frozen for Foundation Phases)
• Local database is the single source of truth.
• All financial and document state changes occur via append-only domain events.
• Supporting identity data may change via explicit CRUD within defined boundaries.
• Projections must be fully rebuildable from events.
• No silent data mutation or in-place edits.
• Migrations are mandatory and written before schema changes.
• UI may not compensate for data inconsistency.
• Cloud sync may lag, replay, or fail without corrupting truth.
• Commands express intent; only aggregates may emit domain events.
• Replay explains history; it must never decide or mutate truth.
• Projection tables may be dropped and rebuilt at any time without data loss.
• Performance optimizations must not introduce new sources of truth.
• Build configuration errors are correctness failures, not tooling issues.
• Room, KSP, and migrations must never appear outside the platform module.
• Event storage schema changes require migration tests before merge.
• Projection writers must never be invoked directly outside the PlatformReplayCoordinator.
• Replay execution order is deterministic and centrally enforced.
• Introduction of alternate replay entry points is a constitutional violation.

• **Invoice-from-Challan Linkage Atomicity Law**
  – When an Invoice is created from a Challan, the creation of the
    Invoice finalization event and the corresponding
    DocumentLinkCreated event **must be atomic**.
  – It must be impossible for a finalized Invoice originating from a
    Challan to exist without its linkage fact.
  – Linkage creation may not be asynchronous, best-effort, or deferred.
  – If atomicity cannot be guaranteed, Invoice finalization must fail.

Rationale:
This law guarantees that document relationships are never partially
materialized, preserves replay determinism, and ensures that all
derived artifacts (including PDFs) remain safely derivable from domain
truth.

UI Design System — Operational Status (AMENDED)

• Verity Light and Dark color palettes are now concretely implemented and
  operationally active.
• Color philosophy is enforced in code:
  – Cool-neutral, graphite-anchored
  – Luminance-driven hierarchy
  – No semantic meaning encoded via color
• Primary (System Backbone) and Accent (Action Emphasis) roles are preserved
  exactly as defined in the Core Seed.
• Accent color remains adjustable, but the structural color contract is locked.

• Exploratory colors are explicitly quarantined as non-system candidates.
• Candidate colors are not accessible via VerityTheme and must never be used
  in production UI.

• VerityButton is now a stable, first-class UI primitive:
  – Two roles only: Primary and Secondary
  – Primary uses system backbone color
  – Secondary uses neutral surfaces with border semantics only
  – Disabled and pressed states are deterministic and theme-driven
  – No accent misuse or ad-hoc styling permitted

• VerityTextField is now a stable, first-class UI primitive:
  – Material-aligned (OutlinedTextField based)
  – Supports SelectionSearch and Basic roles
  – Autocomplete behavior follows the locked UX laws:
      * Typing-first
      * Inline expansion (non-popup)
      * Keyboard focus is never interrupted
      * Suggestions are visually continuous with the input field
  – Filtering and ranking remain upstream responsibilities
  – UI primitives receive pre-filtered suggestion lists only

• Financial UI components (invoice line items, amounts) are now validated against real draft data and considered production‑directional.

• These primitives are no longer experimental.
• Future UI work must compose from these primitives, not bypass or replace them.
• Further changes are limited to visual polish or explicit contract evolution.
